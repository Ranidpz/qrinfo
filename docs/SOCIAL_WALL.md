## 0. למה לא להרחיב את Q.Vote

מבחוץ זה נראה אותו דבר: תמונות, קטגוריות, לבבות ומסך גדול. המיפוי קיים: מועמד ≈ פוסט, קטגוריה ≈ מחלקה, הצבעה ≈ לייק, `isApproved` ≈ מודרציה. אבל מנוע אחר:

| | Q.Vote | Social Wall |
|---|---|---|
| מי יוצר תוכן | עשרות מועמדים, המפיק מאשר | כל משתתף, מאות עד אלפי פוסטים |
| "הצבעה" | משאב נדיר (1–3 לבוחר), הוגנות ומניעת הונאה הן הליבה | לייק לכל פוסט, בלי הגבלה, אין מה "לרמות" |
| זמן | שלבים: הרשמה → הצבעה → תוצאות → גמר | זרם רציף בלי שלבים |
| תוצאה | זוכה | מעורבות + תחרות מחלקות |
| נתונים | `candidates` נכתב מהדפדפן ונקרא בפומבי (חוב אבטחה פתוח, `SECURITY_RULES.md` §12) | הכול נעול מאחורי השרת, אירוע סגור |

הרחבת Q.Vote הייתה גוררת את השלבים, הגמר ומגבלות ההצבעה, ואת נתיב הכתיבה מהדפדפן שסותר "אירוע סגור". בנוסף, זה מסכן לקוחות חיים של Q.Vote.
**לכן:** מנוע חדש (`socialwall`) שממחזר את החלקים של Q.Vote ו-Selfie Beam: צנרת תמונות, עורך מיתוג, גריד ה-Beam, OTP ושער הדפדפן המובנה.
**שיווקית** זה "הדור הבא של מה ש-ToMix אהבו". בהמשך הליבה המאובטחת יכולה לשמש גם את Q.Vote (ולסגור את החוב שלו), ומצב "הכתרה" בסוף היום מחזיר את חוזק ההצבעה לתוך הקיר.

## 1. העיקרון

הלקוחות הם חברות גדולות. אירוע אחד שבו תמונה לא הולמת עולה על LED, או שהמערכת נופלת מול 250 עובדים, שורף את הערוץ (המפיק) ולא רק את הלקוח.
לכן שלושה כללים מעל כל פיצ'ר:

1. **שום דבר לא מגיע למסך בלי שליטה של מפעיל**, ויש כפתור חירום שמקפיא או מחשיך את המסך בלחיצה.
2. **כל הנתונים מאחורי השרת.** הדפדפן לא קורא ולא כותב שום מסמך של משתתף או פוסט ישירות.
3. **כל פעולה ניתנת לחזרה בלי כפילויות:** העלאה, לייק ומחיקה הן אידמפוטנטיות, כי רשת של אירוע נופלת.

## 3. מודל נתונים

### 3.1 הגדרות (ציבורי, על מסמך הקוד)
`codes/{id}.media[].socialWallConfig` — **ציבורי, בלי סודות**. להוסיף ל-whitelist ב-`db.ts` (`updateQRCode`).

```ts
interface SocialWallConfig {
  eventTitle: string;
  branding: { logoUrl?: string; primaryColor?: string; screenSideText?: string; /* ... */ };
  locale: 'he' | 'en';                 // UI; מחלקות יכולות להיות באנגלית בכל מקרה
  departments: { id: string; label: string; color?: string }[];  // רשימה סגורה, אין טקסט חופשי
  access: 'pin' | 'pin_whatsapp' | 'allowlist';                   // V1: 'pin'
  feedModeration: 'post' | 'pre';      // post = עולה לפיד מיד, מפעיל יכול להסתיר
  screenModeration: 'manual' | 'delayed';
  screenDelaySec?: number;             // ל-'delayed', ברירת מחדל 60
  captionMax: number;                  // ברירת מחדל 120
  maxPostsPerMember: number;           // ברירת מחדל 40
  uploadsOpen: boolean;                // מתג סגירה
  feedOpen: boolean;                   // מתג סגירה
  eventEndsAt?: string;                // ISO, מפעיל את ספירת השמירה
  retentionDays: number;               // ברירת מחדל 30 אחרי סוף האירוע
}
```

### 3.2 סודות
`codes/{id}/private/secrets`, להוסיף ל-`SECRET_FIELDS` ב-`src/lib/codeSecrets.ts`:
- `socialWallPin`: קוד אירוע, 6 תווים מאלפבית בלי תווים מבלבלים (`crypto.randomInt`)
- `socialWallScreenKey`: מפתח למסך ה-LED (`randomBytes(16)`)
- `socialWallModKey`: מפתח לקישור המפעיל בשטח (אנשי ToMix בלי חשבון)

כל השוואה של סוד נעשית בשרת עם `timingSafeEqual`, לעולם לא בדפדפן.

### 3.3 נתוני משתתפים (Admin SDK בלבד, rules `if false`)
מודול אחד: `src/lib/socialwall/store.ts` (לפי התבנית של `src/lib/qbet/store.ts`).

```
codes/{id}/swMembers/{memberId}
  name, departmentId, status: 'active'|'blocked',
  sessionHash (sha256 של הטוקן), postCount, lastPostAt,
  phone? (רק ב-access שאינו 'pin', מנורמל), createdAt, lastSeenAt

codes/{id}/swPosts/{postId}            // postId = UUID שנוצר בטלפון → העלאה חוזרת לא יוצרת כפילות
  memberId, authorName, departmentId,  // צילום מצב של השם בזמן הפרסום
  caption, fullUrl, cardUrl, storageKeys[], bytes, width, height,
  status: 'pending'|'visible'|'hidden'|'deleted',
  screen: 'queued'|'approved'|'rejected', screenEligibleAt,
  likeCount, pinned?, createdAt, updatedAt, moderatedBy?, moderatedAt?

codes/{id}/swLikes/{postId}__{memberId} // מזהה דטרמיניסטי → לייק כפול בלתי אפשרי
  postId, memberId, createdAt

codes/{id}/swAudit/{autoId}            // כל פעולת מודרציה: מי, מה, מתי (נדרש בארגונים)
  action, postId?, memberId?, actor: 'owner:{uid}'|'mod-link', at
```

ל-`firestore.rules`:
```
match /swMembers/{d} { allow read, write: if false; }
match /swPosts/{d}   { allow read, write: if false; }
match /swLikes/{d}   { allow read, write: if false; }
match /swAudit/{d}   { allow read, write: if false; }
```
אינדקס מורכב אחד: `swPosts (status ASC, createdAt DESC)`. לפרוס לשני הפרויקטים ולוודא בקונסול (ה-CLI מדלג בשקט).

### 3.4 "דופק" בזמן אמת (RTDB)
הבעיה: כל הנתונים נעולים, אבל הפיד והמסך צריכים להתעדכן חי.
הפתרון: צומת אחד ב-RTDB שמחזיק **רק מספר**, `socialwall/{codeId}/rev`. השרת מעלה אותו בכל פוסט חדש ובכל פעולת מודרציה. הלקוחות מאזינים לו ושולפים מה-API רק כשהוא משתנה (debounce של 3–5 שניות, עם cursor `since`).
התוכן לא נחשף בשום שלב. הדופק חושף רק "קרה משהו".

```json
"socialwall": { "$codeId": { "rev": { ".read": true, ".write": false } } }
```
לייקים לא מעלים את הדופק. ספירות הלייקים מתרעננות כל 15–20 שניות כשהדף גלוי, או עם הדופק הבא.

## 4. זהות וכניסה

> **עודכן:** בפועל נבנו ארבעה מצבים לבחירת הלקוח: `open` (שם + מחלקה), `whatsapp`, `allowlist`, `allowlist_whatsapp`.
> קוד אירוע (PIN) לא נבנה. ברשימה בלי וואטסאפ, מי שיודע טלפון של עובד נכנס בשמו (כתוב בעורך). שם/מחלקה מהרשימה גוברים על מה שהוקלד.
> **4.0 OTP בוואטסאפ:** 6 ספרות, 5 דקות, 5 ניסיונות לקוד. בנוסף 10 טעויות לטלפון בשעה שלא מתאפסות בשליחה חוזרת (אחרת שליחה כל 45 שניות מאפשרת ניחוש בלי סוף).
> סשן = `memberId.token` (24 בתים, נשמר רק hash, עד 3 מכשירים), ב-header `x-sw-session`.

### 4.1 (היסטורי) קוד אירוע
1. ה-QR מוביל ל-`/v/{shortId}#k=PIN`. הקוד יושב ב-fragment, שלא מגיע לשרת ולא נכנס ללוגים. אפשר גם להקליד ידנית.
2. `POST /api/socialwall/join` עם `{codeId, pin, name, departmentId}`. השרת מאמת, יוצר member ומחזיר `{memberId, token}`. הטוקן הוא `randomBytes(32)`, ובמסד נשמר רק ה-hash שלו.
3. הטלפון שומר את שניהם ב-`localStorage['sw_{codeId}']` ושולח `Authorization: Bearer {memberId}.{token}` בכל קריאה.
4. אם המשתתף נמצא בדפדפן מובנה (וואטסאפ), מציגים את שער "פתח בדפדפן" (`src/lib/inAppBrowser.ts`), כי ה-localStorage שם מבודד.

**ניחוש קוד:** קוד של 6 תווים מ-31 תווים נותן ~887M אפשרויות. מעבר לזה, מגבלה עמידה ב-Firestore (`rateLimits`) של 30 כישלונות לכל קוד+IP ב-10 דקות. רשת האירוע משותפת לכולם, ולכן לא נועלים IP לגמרי, רק מאטים. מעבר לסף גלובלי לקוד, המפעיל מקבל התראה ויכול לסובב את הקוד.

**הסיכון שנשאר:** מי שמצלם את הפוסטר בכניסה יכול להיכנס. עבור יום כיף זה סביר, כי המפעיל יכול לחסום משתתף ולהסתיר את כל הפוסטים שלו בלחיצה. אם הלקוח דורש יותר → V1.1.

### 4.2 V1.1: וואטסאפ או רשימת HR
- `pin_whatsapp`: קוד + OTP דרך `guardedSendOTP` בלבד. משתתף אחד לכל טלפון.
- `allowlist`: HR מעלים רשימת טלפונים, ורק הם יכולים לאמת. זו האפשרות הכי חזקה, אבל אז אנחנו מחזיקים מידע אישי מהלקוח. נדרשת מחיקה בסוף, וייתכן שגם DPA.

## 5. ממשקי API

| נתיב | גישה | מה עושה |
|---|---|---|
| `POST /api/socialwall/join` | ציבורי + קוד אירוע | יצירת משתתף, החזרת טוקן |
| `POST /api/socialwall/posts` | משתתף | העלאה (multipart: file, postId, caption) |
| `DELETE /api/socialwall/posts` | משתתף (שלו בלבד) / מפעיל | מחיקה |
| `GET /api/socialwall/feed` | משתתף | עמוד ראשון, או `since=` לדלתא, או `cursor=` לגלילה, `dept=` |
| `POST /api/socialwall/like` | משתתף | `{postId, on}`, אידמפוטנטי |
| `GET /api/socialwall/screen` | מפתח מסך | רק פוסטים מאושרים למסך + סיכומי מחלקות |
| `POST /api/socialwall/moderate` | בעלים (`requireCodeOwner`) או מפתח מפעיל | approve / hide / reject-screen / pin / block-member |
| `POST /api/socialwall/control` | בעלים או מפתח מפעיל | `uploadsOpen` / `feedOpen` / `screenState` (live, frozen, slate) |
| `GET /api/socialwall/export` | בעלים | רשימת כל התמונות המאושרות לייצוא |

כללים לכל הנתיבים: אימות כל שדה (סוג, אורך, enum), `ownerId` נגזר תמיד מהקוד, הודעות שגיאה כלליות בלבד, ובלי טוקנים או טלפונים ב-URL.
מגבלות in-memory לכל IP: נדיבות (`RATE_LIMITS.GAME`, כי כל האולם על IP אחד). המגבלות האמיתיות הן **לכל משתתף, עמידות, על מסמך המשתתף**.

### 5.1 העלאה: הנתיב הכי קריטי
**בטלפון:** חיתוך והקטנה ל-1600px בצד הארוך, WebP q0.82, ונפילה ל-JPEG כשהדפדפן לא מקודד WebP (iOS < 17, אותו טריק של `cropImageToSquareWebp`). התוצאה < 700KB, הרבה מתחת ל-4.5MB של Vercel.
התור: `uploadQueue` עם retry ו-backoff. ה-`postId` נוצר לפני הניסיון הראשון, כך שניסיון חוזר לא יוצר כפילות. בפיד מוצגת התמונה מקומית מיד (`localPreview`) עם סטטוס "מעלה…" או "נכשל, נסה שוב".

**בשרת, לפי הסדר:**
1. אימות משתתף פעיל, `uploadsOpen`, `postCount < maxPostsPerMember`, לפחות 8 שניות מ-`lastPostAt`.
2. בדיקת סוג הקובץ לפי **magic bytes** ולא לפי ה-mime שהדפדפן הצהיר. מקסימום 5MB.
3. Sharp: `limitInputPixels` (הגנה מפצצת דקומפרסיה), `.rotate()` לפי EXIF, ואז **מחיקת כל המטא-דאטה**. תמונות מטלפון נושאות מיקום GPS, ואסור שהוא יגיע לפיד של 250 איש. מפיקים שני גדלים: `full` 1600 ו-`card` 720.
4. העלאה ל-R2 תחת `{ownerId}/{codeId}/socialwall/{postId}/…` (מפתח לא ניתן לניחוש). עדכון `storageUsed` של הבעלים בשרת.
5. `create()` של מסמך הפוסט. אם הוא כבר קיים (ניסיון חוזר), מחזירים את הקיים ולא מעלים שוב.
6. בטרנזקציה אחת: עדכון `postCount` ו-`lastPostAt`, ואז העלאת הדופק.

אם R2 הצליח אבל המסמך נכשל, נשאר קובץ יתום. ניקוי יומי משווה את `swPosts` לרשימה ב-R2 תחת התחילית של הקוד.

### 5.2 לייקים
טרנזקציה: קריאת `swLikes/{postId}__{memberId}` ← (אם צריך) create/delete + `increment(±1)` על הפוסט. קודם כל הקריאות, אחר כך הכתיבות (Lessons Learned).
פוסט "חם" הוא נקודת עומס. ב-250 משתתפים הטרנזקציות מסתדרות עם retry. ב-1,000+ צריך לעבור למונה מפוצל (shards). זה נבדק בבדיקת העומס.
**סיכומי המחלקות לא נשמרים כמונה** (זה היה מסמך חם שכל לייק פוגע בו). המסך מחשב אותם מרשימת הפוסטים שכבר אצלו.

## 6. מודרציה

**ברירת מחדל מומלצת לארגונים:**
- פיד: `post`. הפוסט מופיע מיד, והמפעיל יכול להסתיר.
- מסך: `delayed`, 60 שניות. פוסט עולה למסך רק אם אף אחד לא הסתיר אותו בדקה הראשונה. לאירוע רגיש במיוחד: `manual`, כלומר רק מה שמפעיל אישר.

**פאנל מפעיל** (בדשבורד, ובקישור `?mod=` לצוות ToMix בטלפון):
- תור "בדרך למסך" עם ספירה לאחור, וכפתורי הסתר / אשר עכשיו / נעץ.
- חסימת משתתף: מסתירה את כל הפוסטים שלו, מבטלת את הטוקן, וחוסמת כניסה מחדש עם אותו שם במכשיר.
- **כפתור חירום** (תמיד גלוי, אדום): `screenState = 'slate'`. המסך עובר לשקופית מותגת תוך פחות משנייה, דרך הדופק. `frozen` מקפיא את הגריד הנוכחי.
- מתגים: סגירת העלאות, סגירת הפיד.
- כל פעולה נרשמת ב-`swAudit`.

## 7. מסך ה-LED

נתיב: `/v/{shortId}?screen=1#key=…` (המפתח ב-fragment, ונשלח ב-header). רכיב: `SocialWallScreen`.
- גריד בהשראת ה-shuffle של `GalleryClient`, כולל אותו אלגוריתם בלי כפילויות סמוכות. כל תא מציג תגית מחלקה ולבבות. פוסט חדש נכנס עם רגע spotlight. פאנלי מיתוג בצדדים, כמו בהדמיות. טבלת מחלקות.
- **שרידות לנפילת רשת:** כל תמונה נטענת מראש ל-blob מקומי (תבנית `useLocalCopy` מ-10 בול). כשאין רשת, המסך ממשיך להתחלף מהמטמון ולא מציג שגיאה לקהל. נקודה קטנה בפינה (רק למפעיל) מראה את מצב החיבור.
- פעימת לב: המסך מדווח כל 30 שניות, והפאנל מציג "המסך מחובר / לא דיווח X שניות".
- הגדרות מקומיות למסך (עמודות, קצב, גודל) לפי התבנית של `BeamControlPanel`.
- ממליצים ללקוח: מחשב ייעודי למסך על חיבור 4G/קווי, לא על ה-Wi-Fi של הקהל.

## 8. פרטיות, שמירה ואמון

- דפים `noindex`. תצוגת קישור (OG) של האירוע: לוגו בלבד, לעולם לא תמונות משתתפים.
- טלפונים (אם יש) מוסתרים בכל תגובת API שאינה לבעלים, ולא נכנסים ללוגים.
- **שמירה:** `retentionDays` אחרי `eventEndsAt`. cron מוחק פוסטים, לייקים, משתתפים וקבצי R2, ומשאיר רק סטטיסטיקה אנונימית. כפתור "סיים אירוע ומחק עכשיו" לבעלים.
- **ייצוא ל-HR** לפני המחיקה: ZIP בצד הלקוח מכתובות `full` (צריך לוודא CORS ב-R2), או רשימה ב-CSV/XLSX בצד הלקוח.
- **סיכון ידוע:** כתובות התמונות ב-R2 ציבוריות. המפתח לא ניתן לניחוש והדלי לא ניתן לרישום, אבל קישור שהועבר ייפתח. זו אותה רמה כמו צילום מסך. ל-V2: קישורים חתומים.
- **דף אמון ללקוח** (עמוד אחד): איפה הנתונים (Firebase/Google Cloud, Cloudflare R2, Vercel), הצפנה בתעבורה ובמנוחה, מי ניגש, זמן שמירה, מחיקה לפי בקשה, ספקי משנה. חברה כמו KLA עשויה לשלוח שאלון ספקים. עדיף שיהיה מוכן מראש.

## 9. אמינות: מה חייב לקרות לפני האירוע הראשון

**יעד עומס (פי 2 מ-KLA):** 500 משתתפים, 2,000 פוסטים, 20,000 לייקים, שיא של 5 העלאות בשנייה, 100 בקשות פיד בשנייה.

1. **בדיקת עומס** על `qrinfo-dev`: `scripts/load/socialwall.mjs` מדמה משתתפים (join, העלאה, פיד, לייקים) ובודק שאין כפילויות, שהספירות מדויקות ושה-latency סביר.
2. **בדיקות יחידה** ללוגיקה טהורה (`src/lib/socialwall/rules.ts`: אימות קלט, החלטות מודרציה, זמני מסך, מגבלות): `scripts/tests/socialwall.test.mjs`.
3. **חזרה גנרלית** עם מסך אמיתי וטלפונים אמיתיים (iPhone ישן, Android, דפדפן וואטסאפ).
4. `npm run security:check` נקי, rules ואינדקס פרוסים לשני הפרויקטים ומאומתים בקונסול.
5. לוודא שה-region של פונקציות Vercel קרוב ל-region של Firestore (latency בכל קריאה).

**צ'קליסט לפני אירוע** (להוסיף לסעיף 11 ב-`SECURITY_RULES.md`):
- [ ] קוד אירוע שגוי נדחה, קוד נכון נכנס
- [ ] העלאה ברשת חלשה (throttling) מסתיימת ולא מכפילה
- [ ] הסתרה מהפאנל מורידה מהמסך תוך פחות מ-5 שניות
- [ ] כפתור החירום מחשיך את המסך תוך פחות משנייה
- [ ] ניתוק הרשת של מחשב המסך: הגריד ממשיך להתחלף
- [ ] קישור המסך וקישור המפעיל לא נפתחים מה-QR הציבורי
